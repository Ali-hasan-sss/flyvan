# خطة التنفيذ — Fly Van

تاريخ الفحص: 2026-10-19.

## المرحلة 0 — وضع المستودع

المستودع كان حزمة بداية، وليس تطبيقًا:

- `.cursor/rules/permissions.mdc`: قواعد الصلاحيات والأمان والمالية. تبقى مرجعًا ملزمًا.
- `PROMPT_CURSOR.md`: البرومبت المرحلي. يبقى مرجع النطاق.
- `README.md`: تعليمات تشغيل الحزمة داخل Cursor.

لم يكن هناك Git، ولا تطبيقات، ولا مخطط قاعدة بيانات، ولا اعتمادات.

بيئة الجهاز وقت الفحص:

- Node.js 24.13.1
- npm 11.6.0
- pnpm 10.10.0
- Docker 28.0.4
- Docker Compose 2.34.0

لم يُحذف شيء قائم. تعليمات الحزمة استُبدلت بدليل تشغيل المشروع بعد إنشاء الأساس، مع الإبقاء على ملفات القواعد والبرومبت.

## قرار المعمارية

Monorepo بأداة pnpm workspaces وTurborepo، وتطبيقات معيارية داخل عملية واحدة للواجهة البرمجية (Modular Monolith). لا Microservices في الإصدار الأول.

```text
apps/web       Next.js — لوحة الإدارة والصفحات العامة، عربية RTL
apps/api       NestJS — REST وSwagger وفحص الصحة
apps/mobile    Expo — هيكل تطبيق السائق
packages/database  Prisma 7 وPostgreSQL
packages/types     عقود وأنواع وقواعد حساب مشتركة
packages/ui        رموز الهوية البصرية والمكونات المشتركة
packages/config    إعدادات TypeScript المشتركة
```

PostgreSQL هو مصدر الحقيقة. Redis غير مضاف لأنه لا توجد مهام خلفية بعد.

## ما تنفذه المرحلة 1

- أدوات المستودع: pnpm وTurbo وTypeScript الصارم وESLint وPrettier.
- Docker Compose لـ PostgreSQL المحلي.
- مخطط Prisma الأول وترحيله وبذر تطوير آمن.
- هوية بصرية واحدة عبر متغيرات CSS ورموز TypeScript.
- هيكل صفحات عربية يوضّح أن وحدات التشغيل لم تُربط بعد، مع فحص صحة حقيقي للواجهة البرمجية.
- وثائق التشغيل والافتراضات.

## المرحلة 2 — المصادقة والصلاحيات

نُفذت: تسجيل الدخول بالبريد أو الهاتف، تدوير رمز التحديث وإبطاله، تعطيل المستخدم مع إبطال جلساته، وإدارة المستخدمين لمالك المنصة مع سجل تدقيق. الاختبارات تغطي رفض الدخول الخاطئ، وإعادة استخدام رمز التحديث، ومنع الكونترول والمدير من `USERS_MANAGE`.

## المرحلة 3 — السائقون والمركبات والمناطق

نُفذت: إنشاء سائق بحساب `DRIVER`، تسجيل مركبة وإسنادها، بيانات الوثائق من دون رفع ملف، واعتماد السائق أو المركبة فقط بعد وثيقة معتمدة غير منتهية. مناطق الخدمة تُنشأ وتُربط بطلب من السائق ثم مراجعة إدارية. قبول المنطقة لا يسند رحلة. معاينة المطابقة متاحة للكونترول من دون إنشاء عرض.

## ما لا تنفذه المراحل 1–3

الحجوزات والرحلات والإسناد الفعلي، والدفتر المالي التشغيلي، والتقارير، وقبول الرحلة من تطبيق السائق. لا تُعرض بيانات تشغيلية وهمية على أنها سجلات حقيقية.

## المرحلة 4 — الحجوزات والرحلات

نُفذت: إنشاء حجز مؤكد من الكونترول دون حساب راكب، مع أجرة مثبتة ورحلة واحدة لكل اتجاه. الإياب حجز مستقل. الإلغاء بسبب مسجّل، وتعديل الأجرة بعد التثبيت لمالك المنصة فقط. الإسناد اليدوي لسائق جاهز، وعرض الرحلة إذا سمح القرب أو منطقة الخدمة، ثم قبول السائق أو رفضه. حالات الرحلة والصعود وعدم الحضور واستلام الأجرة النقدية مسارات تشغيلية. إكمال الرحلة أو إلغاؤها لا ينشئ عمولة، وفحص حد المديونية مؤجل.

## المرحلة 5 — العمولات والدفعات وحد المديونية

نُفذت: سياسة عمولة افتراضية ونسبة خاصة بالسائق مع تاريخ سريان، من دون إعادة كتابة العمولات السابقة. إكمال رحلة فيها راكب صاعد ينشئ عمولة واحدة وقيد مدين بمفتاح `commission:{tripId}`. الرحلة الملغاة واستلام أجرة الراكب نقدًا لا ينشئان قيدًا. موظف المالية يسجّل الدفعة، ومالك المنصة يعتمدها فيُوزَّع المبلغ على أقدم العمولات. الدفعة الجزئية تخفض الرصيد بمقدارها، والزيادة تبقى رصيدًا دائنًا. الإسناد وقبول العرض يفحصان الحد داخل معاملة مع قفل صف الحساب. غياب الحد أو تجاوزه يمنع ذلك السائق فقط، مع استثناء موثق لمالك المنصة على الرحلة.

## المرحلة 6 — تطبيق السائق

نُفذت: شاشة المالية تقرأ رصيد العمولة والحد والتسديدات من `GET /api/finance/me`، وتفصل أجرة الراكب النقدية عن عمولة الشركة. العروض المعلقة تُقبل أو تُرفض من قائمة الرحلات. تفضيل الطلبات القريبة يُحفظ من الملف. الخريطة والصعود وبدء الرحلة وإنهاؤها كانت مربوطة مسبقًا وتبقى على بيانات الرحلة المسندة.
